现状诊断：阅读被当成"打卡"了

当前小程序里，阅读和其他 12 种任务（作业、运动、家务…）共用同一套流程：
创建「阅读 30 分钟」→ 到时完成 → 写一句费曼反馈（remark，上限 400 字）。

这套流程对"运动 30 分钟""练字 15 分钟"这种过程型任务是合适的——做完就是做完。
但对"阅读"这种理解型任务，它丢掉了最关键的东西：

有效阅读环节它在解决什么现有小程序的空缺
选书 · 带目的先问"我为什么读这本书"，避免盲目翻创建任务只填书名和时长，没有"为什么读"
预读看目录/序言，先提出问题，带着问题读完全没有——直接进入"读30分钟"
笔记摘录 + 思考，把书变成自己的只有完成时写一句反馈，读的过程没有笔记入口
专题输出读完整合成一篇"这本书教了我什么"没有——读完就结束了，散落的反馈没归档
巩固间隔复习，让知识留下来没有——没有复习提醒机制
核心判断
别把"有效阅读"做成六个孤立新功能，而是让现有闭环"变深"。
现有闭环：创建 → 阅读 → 完成反馈 → 统计，已经能承载方法论，只是每步"浅"了。
正确做法是在每个已有节点上，把一次提问变成一段引导，渐进式加深，而不是一次性堆砌。

P1 功能：阅读专题 + 巩固复习

阅读专题的本质
把"一本书"当成一个长周期的"项目"，而不是一次任务。
现有模型里，一本书可能被拆成多个"读30分钟"任务，但它们彼此孤立。
阅读专题把它们串起来：同一个 subcategory（书名/专题名）的任务归到一组，
读完后自动生成"这本书教会了我什么"的专题小结。

数据模型：复用预留字段，最小改动

好消息是 server/routine.ts 的 Routine.Info 已经预留了所需字段，基本不需要动后端结构。

预留字段类型如何承载阅读方法论
subcategory number 阅读专题的标识（书名/专题 ID）——同 subcategory 的阅读任务归为一组，组成"阅读专题"
detail string 任务内容 = 书名。阅读目的可以存成一个约定格式，或单独字段
remark string 结构化笔记——用约定分隔符同时承载「摘录 + 思考」两条，或拆成两个字段
mediaRemark string 笔记的图片/语音（拍下书页、录一句感想）——配合之前的语音方案
medias string 预留，可存笔记的多张图片
新增需求建议方案说明
阅读目的 新增 readingPurpose?: string 字段，或在 detail 内约定 建议独立字段，语义更清晰
摘录 vs 思考 新增 quote?: string（摘录），remark 保留为"思考" 复用现有 remark 作为思考，仅新增一个 quote 字段
预读问题 可复用阅读目的字段，或新增 preQuestions?: string 预读问题本质就是阅读目的的一种形态
复习节奏 前端基于 finishTime 计算间隔，配合推送能力 不需要新增字段，前端算 1/3/7/30 天即可
后端改动可以极小。
核心只新增 1-2 个可选字段（readingPurpose、quote），
阅读专题用 subcategory 分组，复习用 finishTime 前端计算。
剩下的全是前端交互和 UI 的工作。

联动点怎么连价值
好奇 → 阅读目的 创建阅读任务时，可以直接从"好奇清单"里选一个问题作为阅读目的 回答"为什么读"的答案，来自之前积累的好奇——选书不再盲目
阅读笔记 → 问答 笔记里"我的思考"如果是个疑问，可以一键转成"问答任务"去深挖 阅读中产生的新问题，进入问答任务，形成知识延展
巩固 → 好奇心再触发 复习时如果又冒出新的"咦"，回到好奇清单 形成"好奇→阅读→输出→新好奇"的飞轮
完整飞轮
好奇 → 选书带问题 → 阅读记笔记 → 专题输出 → 复习巩固 → 冒出新好奇。
这六个环节串起来，恰好把小程序从"打卡工具"升级成"学习闭环工具"。
而每一步都建立在现有能力上，不是另起炉灶。

落地优先级建议

阶段做什么改动量为什么是这一步
第一批 笔记结构化（摘录+思考）+ 阅读目的 前端为主，后端 +1 字段 改动最小，但立刻让"阅读"和其他任务有了本质区别
第一批 预读热身（3 步引导） 纯前端 零后端成本，直接引入"带着问题读"
第二批 阅读专题（聚合 + 专题输出） 前端 + subcategory 分组逻辑 需要先有笔记，专题才有东西可聚合
第二批 巩固复习（间隔提醒） 前端 + 推送能力 依赖推送能力（P0 已规划）就绪
一句话总结：
不要新增一个"阅读 App"——而是让"阅读任务"这一格，在现有闭环里变得更深。
先做笔记结构化 + 阅读目的 + 预读热身这三件轻量的事，
就能让"读 30 分钟"从打卡，变成一次真正的有效阅读。
