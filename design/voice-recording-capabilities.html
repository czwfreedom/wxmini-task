语音反馈 · 全链路能力分析

把"打字填反馈"改成"按住说话"，涉及前端录音 → 文件上传 → 服务端存储 → 回放加载四个环节。 下面逐层拆解每层需要的具体能力。

核心流程

① 前端
按下录音
→
② 微信 API
获取音频文件
→
③ 网络
上传到服务器
→
④ 服务端
存储 + 转文字
→
⑤ 前端
加载回放

第一层：前端录音能力（小程序端）

能力点微信 API / 方案状态备注
录音核心 wx.getRecorderManager() 原生支持 微信官方录音管理器，全局唯一实例
录音格式 format: 'mp3' | 'aac' 原生支持 建议 mp3，兼容性最好，文件也小
麦克风权限 scope.record 原生支持 首次使用会弹系统授权弹窗，用户拒绝后需引导去设置页
开始/停止录音 recorder.start() / recorder.stop() 原生支持 绑定按下/松手手势：touchstart → start，touchend → stop
录音时长限制 duration: 60000（毫秒） 原生支持 建议限制 60 秒，小朋友一句话够了。超时自动触发 onStop
实时音量帧 recorder.onFrameRecorded(res) 原生支持 每帧返回音量数据，可驱动声波动画（如 V2 设计的波纹条）
录音状态回调 onStart / onStop / onPause / onError 原生支持 onStop 回调中得到 tempFilePath（临时音频文件路径）
手势长按 WXML bindtouchstart / bindtouchend 原生支持 "按住说话"的标准实现：touchstart=开始录音，touchend=停止并上传

需要注意的坑：
① RecorderManager 不支持暂停/恢复（pause/resume 在旧版基础库有兼容问题），建议只做"按住录、松手停"的简单模式。
② iOS 和 Android 的录音格式行为不完全一致，建议统一指定 format: 'mp3' + sampleRate: 16000 + encodeBitRate: 48000。
③ 录音过程中如果微信进入后台或被电话打断，onError 会触发，需要有降级提示。

第二层：录音播放（回放自己的声音）

能力点微信 API / 方案状态备注
本地临时文件播放 wx.createInnerAudioContext() 原生支持 录音完成拿到 tempFilePath 后，立即用 InnerAudioContext 播放
远程文件播放 同上，src 指定为远程 URL 原生支持 历史反馈的音频需要从服务器加载，src 设为 CDN 地址
播放状态监听 onPlay / onEnded / onError / onStop 原生支持 驱动播放按钮的 UI 状态变化
播放完成后的自动 UI onEnded 回调触发"完成 ✓"按钮出现 前端逻辑 听完自己的声音后，自动展示"完成"和"重新说"两个按钮

第三层：文件上传

能力点微信 API / 方案状态备注
上传到服务器 wx.uploadFile({ url, filePath, name }) 原生支持 把录音的 tempFilePath 通过 uploadFile 发到后端
上传进度 uploadTask.onProgressUpdate() 原生支持 小文件（几十 KB）基本瞬间传完，进度条可能一闪而过
上传与 completion 的耦合 上传完成 → 获得音频 URL → 赋值到 remark 字段一起提交 需设计 流程：上传音频 → 拿到 URL → Routine.update({ id, mediaRemark: url })
网络异常容错 uploadFile 失败 → 保留 tempFilePath → 允许重试 需设计 录音已产生，不能因为上传失败就丢了。需要在本地暂存并重试

上传策略建议：
① 录音文件很小（60 秒 mp3 约 100-200KB），上传通常秒级完成。
② 建议上传到独立的媒体文件接口（如 /v1/media/upload），返回 CDN URL 后，再将 URL 写入 Routine.update({ mediaRemark: url })。
③ 也可以直接把音频文件附加在 Routine.update 请求里用 multipart 上传，看后端现有架构。如果后端只接受 JSON，就需要先走独立上传接口。

第四层：服务端能力

能力点需要什么当前有无备注
音频文件接收 接口接受 multipart/form-data，接收 mp3 文件 未知 现有的 Network.post 是 JSON 传输，需要新增文件上传接口
文件持久存储 对象存储（OSS/S3/CDN），返回可访问的 URL 需新增 小程序内播放需要 HTTPS 的公网 URL
转文字（可选） 语音识别服务——微信有"同声传译"插件或第三方 ASR 需新增 把录音自动转成文字，并存到 remark 字段，便于搜索和回顾
字段扩展 Routine.Info 新增 mediaRemark 字段（已预留！） 已预留 server/routine.ts 中 Routine.Info 已有 mediaRemark 字段
音频 CDN 回源 存储到 CDN 后，播放端通过 HTTPS 直接拉取 需配置 标准 CDN 配置即可

关于语音转文字（ASR）：
① 如果后端加了语音识别，录完音上传后自动转成文字存到 remark 字段——用户看到的是文字，想听可以点播放听原声。这是最理想的体验。
② 小程序端也有方案：微信有"同声传译"插件（WechatSI），可调用微信的语音识别，无需后端开发。但准确率和可用性需要测试。
③ 如果暂时不做 ASR，音频就只作为 mediaRemark 存储在卡片上——卡片展示一个播放按钮，点一下听原声。也不差。

第五层：数据模型与 UI

能力点方案状态备注
存储模型 Routine.Info.mediaRemark 存音频 URL
Routine.Info.remark 存转写后的文字（或空）		 字段已预留 mediaRemark 在 routine.ts 58 行已定义
卡片 UI 已完成的卡片上，反馈区域从纯文本 → 播放按钮 + 转写文字 需开发 如果只有音频没有文字，卡片展示▶️ 播放图标 + "点击听反馈"
历史兼容 老任务只有 remark 文字，没有 mediaRemark → 正常显示文字 天然兼容 新字段不影响老数据
降级策略 如果不想说话 → 仍可以点击切换到文字输入模式 需设计 语音是默认推荐方式，但文字输入作为备选始终保留

能力清单总结

小程序端 · 全原生支持

✅ 录音（RecorderManager）
✅ 播放（InnerAudioContext）
✅ 手势（touchstart/touchend）
✅ 文件上传（uploadFile）
✅ 录音权限（scope.record）
✅ 音量帧（onFrameRecorded）

前端开发量集中在 UI 和手势交互上，微信 API 已全覆盖。

需后端新增

❓ 文件上传接口（multipart）
❓ 对象存储（OSS/S3）
❓ CDN 域名配置
❓ （可选）语音转文字

核心是新增一个媒体上传接口 + OSS。

需前端新增

🔨 录制页 UI（麦克风按钮+声波）
🔨 回放页 UI（播放按钮+转写文字）
🔨 权限引导弹窗
🔨 卡片上的播放图标
🔨 文字模式降级入口

最大工作量是 UI 打磨，逻辑不复杂。

最小可行版本（MVP）建议：

第一期：只做录音 + 上传 + 回放。卡片上显示播放按钮，不转文字。
后端新增一个 /v1/media/upload 接口，接收 mp3 文件，存 OSS 返回 URL。
小程序用 RecorderManager + uploadFile + InnerAudioContext 即可闭环。

第二期：接入微信"同声传译"插件做语音转文字，存入 remark。
卡片上同时显示文字摘要 + 可点击播放原声。

第一期预估前端 3-4 天 + 后端 1-2 天即可完成。微信生态对录音的支持非常成熟。
